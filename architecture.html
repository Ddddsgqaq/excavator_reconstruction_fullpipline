Semantically-Aware 3D Reconstruction

A Decoupled Service Architecture Combining VGGT Geometry Prediction and YOLOe Open-Vocabulary Segmentation

1. System Overview

The system is a three-process pipeline that produces 3D reconstructions from images or video, optionally augmented with per-pixel semantic labels supplied by an open-vocabulary segmenter. Geometry inference (VGGT) and segmentation (YOLOe) run as independent FastAPI services in their own conda environments; a Gradio Orchestrator coordinates them and exposes the user-facing UI. A Python module (Elevation) provides a downstream DEM-fitting routine invoked through the VGGT service.

4. Workspace Layout

The workspace acts as a content-addressable cache: every user upload creates a fresh session directory, and every YOLOe invocation creates an immutable per-run subdirectory so that prompt iterations do not overwrite earlier results.

    ├── images/                                    ← extracted frames (PNG)
    ├── yoloe_runs/
    │   ├── run_<ts>_text/                         ← one directory per YOLOe call

5. State Management Notes

  • Per-run isolation. Each YOLOe call writes a self-contained run_<ts>_<mode>/ directory; the Orchestrator's hidden state always points to the most recent run, which is consumed verbatim by the next reconstruction.
  • Upload resets state. A new image/video upload clears all stale state (mask path, semantic-ID map, preview gallery, edit selectors), preventing cross-session contamination of previously cached masks.
  • Conditional model reload. YOLOe.set_classes() is unstable when the prompt arity changes (head/conv shape mismatch), but stable for same-arity changes. The service tracks the last class count per model and reloads only when arity actually differs, avoiding repeated CLIP-text-encoder rebuilds that previously caused OOM.
  • Prediction reuse. predictions.npz is written once per reconstruction and reused by /visualize, /edit_pointcloud, /fit_elevation, and /elevation_viewer_data, avoiding redundant VGGT forward passes during interactive parameter tweaking.
  • Gravity alignment is stateless. gravity_alignment.estimate_gravity is called fresh on each /fit_elevation and /elevation_viewer_data request; the result is persisted in _meta.json alongside the GLB outputs so callers can reuse the same R_align without re-running the estimator.

6. Gravity Alignment & Elevation Viewer

The elevation subsystem has two distinct concerns: (a) estimating which direction is "up" in VGGT's world frame, and (b) building a DEM and serving it to an interactive browser viewer.

6a. Gravity Estimation Cascade

VGGT's world frame is anchored to frame-0's OpenCV camera (X-right, Y-down, Z-forward), so the raw point cloud is generally tilted. gravity_alignment.estimate_gravity runs three estimators in priority order and returns a GravityResult containing R_align (3×3) that rotates the world so Y = elevation:

  1. Trajectory plane (primary). SVD/PCA on camera centers. The plane normal is the direction of least variance. Degeneracy guard: if the second/first PCA eigenvalue ratio is below TRAJ_DEGENERATE_RATIO = 0.1 (trajectory collapses to a line), this source is skipped.
  2. Ground-mask plane (sanity-check / fallback). RANSAC on YOLOe-labeled ground points (semantic ID = 1). Used as a cross-check against the trajectory normal; a warning is emitted if the two normals disagree by more than GRAVITY_DISAGREE_DEG = 10°. Becomes the primary source only when the trajectory is degenerate.
  3. Whole-cloud RANSAC (last resort). RANSAC on the full point cloud, biased toward the trajectory normal as a prior when available. Subsampled to 200 k points for speed.

The chosen normal is oriented so that the bulk of the scene sits on its negative side (i.e. the normal points "up", away from the ground). _shortest_arc_rotation then builds the minimal rotation that maps this normal to (0, 1, 0).

6b. DEM Construction (elevation_plane.py)

  1. Extract world points + per-pixel confidence from predictions.npz.
  2. Call estimate_gravity → R_align.
  3. Rotate all points: pts_aligned = pts_world @ R_align.T * scale_factor. Y is now elevation.
  4. Select ground candidates in the aligned frame:
    • If a semantic ground mask is present: keep masked points within ±5 % of the Y-range around the masked-points median Y.
    • Fallback: lowest ground_percentile % by Y.
  5. Interpolate a grid_resolution × grid_resolution DEM over (X, Z) using scipy.interpolate.griddata (linear, with nearest-fill for holes).
  6. Color vertices by elevation using a matplotlib colormap; build a trimesh.Trimesh.
  7. Export elev_r{N}_{cmap}_aligned_only.glb, _merged.glb, and _meta.json (gravity source, n_grav, R_align, scale_factor, warnings).

6c. Three.js Elevation Viewer (elevation_viewer.html)

Served as a static file by the VGGT service at /static/elevation_viewer.html; the /viewer?session=<dir> endpoint redirects there. On load it calls POST /elevation_viewer_data which returns:

  • points_display — point cloud in GLB display space (matches the Gradio 3D viewer).
  • points_aligned — same points after R_align (Y = elevation).
  • T_display — 4×4 transform baked into the GLB by predictions_to_glb (inv(ext[0]) @ opengl @ rot180y), used to convert aligned coords back to display space.
  • cameras — per-frame extrinsics in raw, aligned, and display spaces.
  • dem — 128×128 DEM grid (elevation values + has_data mask) for hole-fill and volume computation.
  • gravity_source, n_grav, R_align, gravity_warnings.

Viewer features:

  • Gravity-axis overlay. Draws X/Y/Z arrows in aligned space projected into display space via alignedToDisplay(ax, ay, az) = T_display @ R_align @ [ax, ay, az, 1].
  • DEM hole-fill mesh. Builds a triangle mesh from the 128×128 grid; cells with only nearest-fill data are rendered at reduced opacity.
  • Volume selection. Rectangle, circle, or ellipse drawn on the canvas selects DEM cells inside the region. Volume = Σ (elev − min_elev) × cell_area × scale_factor².
  • Gravity alignment diagnostic. A 2D canvas panel shows camera-center trajectory before and after alignment, PCA eigenvectors, and the gravity vector, with a warning badge when trajectory and ground-mask normals disagree.

7. Process Lifecycle

The three services are launched as background processes by start_all.sh; each runs in its own conda environment to isolate the conflicting PyTorch/Ultralytics versions required by VGGT and YOLOe. The orchestrator polls the YOLOe and VGGT /health endpoints to surface service status in the UI.
